  Backend Connectivity

  API Base URL: NEXT_PUBLIC_API_URL (defaults to http://localhost:3000/api)

  Auth mechanism: JWT Bearer token stored in localStorage (auth_token + refresh_token). Google OAuth handled by better-auth at NEXT_PUBLIC_BETTER_AUTH_URL.

  ---
  State Management

  auth-store.ts — Persisted to localStorage (auth-storage):
  - Tracks: user, isAuthenticated, showAuthModal, authStep, authFlow, userAuthStep, providerAuthStep
  - Controls the entire multi-step auth/onboarding modal flow
  - Actions: startUserFlow, startProviderFlow, nextUserStep, nextProviderStep, signOut, etc.

  categories-store.ts — In-memory with 5-minute TTL cache:
  - Auto-fetches on first access via useCategories() hook
  - Computed getters: featuredCategories(), topLevelCategories()

  ---
  Key Data Flows

  Login:

  ▎ SignInForm → POST /auth/login → store tokens → GET /onboarding/status → route to onboarding or dashboard

  User Registration:

  ▎ SignUpForm → POST /auth/register → email OTP → 8-step onboarding (interests, location, profile, experience, docs) → POST /onboarding/complete

  Provider Registration:

  ▎ Same signup → 9-step provider onboarding (bio, skills, coverage, documents) → pending review state

  Service Creation:

  ▎ /dashboard/services/new → collect title/category/plans/addons/images → POST /services (FormData) → redirect to services list

  Bot Chat:

  ▎ BotChatBox generates conversationId on mount → user sends message → POST /support/bot → displays markdown response → no auth required

  Admin:

  ▎ Dashboard with Recharts revenue graphs → manage users (PATCH /users/{id}/status), categories (full CRUD), disputes, services across all providers

  Architecture decisions                                                                                                                                                                   
                  
  - Widget guards: SupportChatWidget only renders for authenticated non-admin users. Admins use the dashboard. Unauthenticated visitors keep the existing BotChatBox.                      
  - REST + WebSocket hybrid: Messages are sent via REST (reliable, includes bot reply in response). WebSocket is used for receiving real-time events from other participants (admin
  joining, status changes, admin's messages).                                                                                                                                              
  - Stable socket callbacks: Callbacks are stored in a useRef so the socket never reconnects when component re-renders.
  - Optimistic updates: User messages appear instantly; replaced with server data on success, removed on failure.                                                                          
  - Status lifecycle: BOT → AWAITING_FOR_ADMIN → ACTIVE_WITH_ADMIN → CLOSED — each state has a different UI (status bar, action buttons, input disabled state).                            
  - Backend bug note: The backend's support:join handler accidentally calls client.leave(room) instead of client.join(room). The frontend still calls it, and will work correctly once the 
  backend is fixed. Admin-side real-time works correctly via support:join_as_admin which is implemented correctly.
